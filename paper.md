# Persistent Coordinate Merkle Trees for Versioned World State: Design, Bounds, and Artifact Evaluation

## Abstract

Large interactive worlds need history, rollback, branching, and selective loading. A versioning layer for them must distinguish two workloads that are often conflated: importing a complete snapshot and committing a known set of edits. This paper presents a coordinate-addressed version model and `chunklog` 0.3.0, a Rust implementation for worlds represented as finite maps from two-dimensional integer coordinates to opaque byte payloads. The implementation uses a typed, versioned canonical object format and a fixed-depth persistent radix Merkle tree. A full-snapshot commit scans all N payloads, whereas an explicit k-coordinate change set republishes only the union of affected sixteen-nibble paths. We prove an upper bound of 16k new branch nodes, k leaves, k payload objects, and one Commit per incremental save, before content reuse; we do not claim that complete snapshot ingestion is O(k).

The implementation verifies BLAKE3 addresses on every object read, validates all branch paths, serializes writers with a repository lock, batches each commit's objects in one SQLite transaction, and publishes its reference only after that transaction commits. The artifact contains 45 integration tests, two CLI unit tests, two OPFS log-codec unit tests, and one doctest, including deterministic state-machine, corruption, path traversal, lock, transaction-ordering, and injected GC-failure cases. On one Windows/NTFS host, the N=1,000 initial-snapshot median falls from 10.427 s with one loose file per object to 47.433 ms with the default SQLite CAS, a 220× improvement; N=10,000 completes in 1.156 s. SQLite k=1 commits take 10–14 ms over N∈{100,1,000}, while logical checkout takes 5–8 ms. A controlled 50-save study reports object-type and byte growth under k ∈ {1,10,100}. An engine integration run imports 2,023 binary mapblocks generated by official Luanti 5.16.1 into 289 vertical-column payloads; the deliberately uniform world deduplicates them to two Blobs. We report positive and adverse results together and scope all claims to the evaluated artifact.

## 1. Introduction

Voxel games, simulators, editors, and CAD systems maintain large states that change locally. Their persistence problem is not only saving the latest state: operators may need to restore after corruption, undo destructive edits, compare versions, or experiment on a branch. A natural abstraction is a finite map from stable keys to payloads. In a voxel world the keys are chunk coordinates and the payloads are engine-defined serialized chunks.

Content-addressed snapshots are not new. Git stores typed Blob, Tree, and Commit objects; Venti addresses immutable blocks by content; persistent data structures share unchanged substructure. The research question addressed here is narrower:

> What guarantees and costs arise when a versioning library exposes coordinate-level changes explicitly and represents snapshots with a persistent coordinate Merkle tree?

This paper reports the resulting Rust implementation, proves an upper bound on incremental structural publication, specifies an integrity and failure model tied to the implementation, and evaluates both a real-engine import and the physical-backend sensitivity of initial import.

### 1.1 Contributions

This paper makes four bounded contributions:

1. **A precise split between snapshot and change-set commits.** `commit_snapshot` has Θ(N) input scanning cost. `commit_changes` receives explicit upserts and removals and performs structural work on their affected radix paths.
2. **A typed persistent coordinate tree.** Coordinates map bijectively to sixteen nibbles. Canonically encoded, content-addressed branches and leaves make path copying deterministic and give an incremental structural publication bound independent of N for fixed-width coordinates.
3. **An integrity and failure model tied to implementation.** Reads verify addresses; object kinds have domain-separated tags; branch-name paths are confined to `refs/heads`; writers are serialized; object transactions precede ref publication; GC marking is fail-closed.
4. **A reproducible artifact evaluation that reports adverse results.** Generators create exactly N unique payloads. Results isolate the loose-file small-I/O pathology and show that one SQLite transaction removes the dominant initial-import bottleneck without changing the Merkle algorithm.

We do not claim invention of content addressing, Merkle trees, persistent tries, snapshot comparability, SQLite batching, or mark-and-sweep collection. We also do not yet claim production-engine performance or a cross-file transaction spanning SQLite and refs.

## 2. Model and Cost Terms

Let C = Z². A world is a finite partial function

```text
W : C ⇀ B,
```

where B is the set of finite byte strings. Let N = |dom(W)|. A change set E = (U,D) contains an upsert map U : C ⇀ B and a removal set D ⊆ C, with dom(U) ∩ D = ∅. Let k = |dom(U)| + |D| and u = |dom(U)|.

The implementation uses BLAKE3 [9] as a hash H. Results about address uniqueness assume collision resistance. A store maps an address to canonical bytes. On read, the returned bytes are rehashed and must match the requested address.

We distinguish the following costs:

- **payload hash bytes:** the number of payload bytes processed by H;
- **structural object publications:** canonical Tree nodes newly offered to the store;
- **new unique objects:** publications not already present by address;
- **logical bytes:** canonical object bytes, excluding filesystem allocation metadata;
- **backend I/O:** file or backend operations;
- **end-to-end latency:** measured wall-clock time.

An object-count bound is not a byte-I/O or latency bound unless object sizes and backend behavior are also specified.

## 3. Canonical Objects

Canonical object wire version 1 defines four domain-separated object types:

- `Blob(payload)`;
- `TreeBranch({nibble → child address})`;
- `TreeLeaf(coordinate, blob address)`;
- `Commit(root address, optional parent, timestamp, message)`.

Every object begins with the magic `CHLG`, format version 1, and a distinct type tag. Integers are big-endian. Variable data is length-prefixed. Branch entries are sorted by nibble. Decoders reject duplicate or out-of-range nibbles, truncation, unknown versions, invalid UTF-8 messages, and trailing bytes. The durable layout is specified independently in `FORMAT.md`.

### Lemma 1: canonical address determinism

For any logical object o, canonical encoding produces one byte string enc(o). Therefore repeated encodings of o have the same address H(enc(o)).

**Proof.** Tags, integer byte order, lengths, field order, and branch order are fixed. No field depends on map insertion order or process-local state. Equal logical fields therefore emit equal byte sequences, and deterministic H returns equal addresses. ∎

Domain-separated tags prevent a payload from aliasing a Tree or Commit merely because its bytes equal the untagged serialization of that object.

## 4. Persistent Coordinate Radix Tree

### 4.1 Coordinate path

The two's-complement big-endian bytes of x followed by z form an eight-byte key. Traversing each byte's high nibble then low nibble yields a path of fixed depth d=16 over alphabet {0,…,15}. This mapping is bijective over pairs of 32-bit integers.

A sparse branch maps present nibbles to child addresses. A leaf at depth 16 repeats its exact coordinate and references a Blob. Readers verify that the repeated coordinate matches the traversed path. An empty world has one empty root branch; empty non-root branches are removed.

### 4.2 Snapshot commit

`commit_snapshot(W,m)` encodes and hashes all N payloads, constructs the canonical radix tree from all N mappings, publishes a Commit, and advances the current reference.

### Proposition 1: snapshot cost

For fixed coordinate width, snapshot construction performs Θ(N) payload visits and O(Nd) structural grouping work, which is Θ(N) because d=16 is constant. Payload hashing processes the sum of all payload lengths.

### 4.3 Incremental commit

`commit_changes(E,m)` reads the parent root, encodes only the u upsert payloads, groups edits by path prefix, and recursively copies branches on the union of affected paths. Children outside that union retain their addresses. A removal of a missing coordinate can reuse the existing root without structural publication.

Let P(E) be the set of distinct non-empty branch prefixes of coordinates in E, including their root prefixes and excluding leaves. Because each coordinate has d prefixes,

```text
|P(E)| ≤ d·k = 16k.
```

### Theorem 1: incremental publication bound

One change-set commit publishes at most |P(E)| branch objects, u Tree leaves, u Blob objects, and one Commit before content reuse. Consequently it publishes at most 16k + 2u + 1 ≤ 18k + 1 objects, and performs O(dk) structural work plus hashing of the upsert payload bytes.

**Proof.** Grouping by the first nibble partitions E. Recursing performs the same partition at each of d levels. A branch is reconstructed only for a prefix containing at least one changed coordinate, so the number of reconstructed branches is at most |P(E)|. Each upsert reaches one leaf and produces at most one Blob; removals produce neither. One Commit records the resulting root. Content addressing can only reduce the number of new unique objects. ∎

This is an upper bound, not an exact closed form. Shared prefixes reduce branch publications; no-op updates may reproduce existing leaves and branches; payload reuse reduces Blob count.

### Corollary 1: independence from world cardinality

For fixed-width coordinates and an explicit change set, the structural bound depends on k rather than N. This does not apply when the caller supplies a complete world and the library must discover changes by scanning it.

## 5. Version Operations

### 5.1 Materialization and comparison

A Commit root uniquely identifies a finite coordinate-to-Blob map, conditional on collision resistance and store consistency. `load` traverses the Tree and reads every Blob. `chunk_hashes` returns sorted coordinate/address pairs; `read_chunk` verifies and decodes one Blob.

The current `diff(u,v)` expands both roots to ordered maps and compares them.

### Proposition 2: total snapshot comparability

Any two well-formed versions can be compared without inspecting their parent histories in O(Nu+Nv) Tree traversal time and memory in the current implementation.

This is a property of self-contained snapshots, not a novelty claim. A future recursive diff could skip subtrees with equal addresses.

### 5.2 Logical checkout

Checkout resolves and verifies one target Commit, acquires the writer lock, and atomically replaces HEAD with a branch reference or Commit address. It does not traverse Tree nodes or Blob payloads.

### Proposition 3: checkout relative to world size

Assuming bounded Commit metadata and branch-name length, logical checkout is O(1) with respect to N. This statement excludes world materialization and engine activation.

### 5.3 References and single-writer semantics

All branch entry points validate names before path construction. Names must be one non-hidden path component without whitespace, separators, or `..`; the resulting path must have `refs/heads` as its direct parent.

Mutating operations create `.chunklog/LOCK` with exclusive creation. Reference data is written to a synced temporary file in the same directory and atomically replaces the destination through the platform implementation used by `atomicwrites`. The default SQLite backend commits object rows with rollback journaling and `synchronous=FULL` before ref replacement. A process crash can still leave immutable unreachable objects or a stale lock; the SQLite transaction and filesystem ref are ordered but do not form one cross-file transaction.

## 6. Garbage Collection

GC executes under the writer lock:

1. snapshot HEAD and all branch roots;
2. mark Commit parent/root edges;
3. mark Tree child/Blob edges while verifying type, address, depth, and coordinate path;
4. enumerate stored addresses and delete unmarked objects.

### Theorem 2: soundness under static roots

If roots do not change during collection, every reachable object is present and well formed, and store reads return addressed bytes, GC deletes no reachable object.

**Proof.** The typed worklists begin with all roots and visit every edge admitted by the canonical Commit and Tree formats. Thus every reachable object is marked before sweep. Sweep deletes only unmarked addresses. The writer lock makes the root set static with respect to supported mutating operations. ∎

### Theorem 3: conditional completeness

If store enumeration returns exactly the stored address set and every requested delete succeeds, GC deletes every stored object outside the reachable set.

**Proof.** After complete marking, sweep visits every stored address and invokes delete exactly when it is unmarked. ∎

### Failure semantics

If a reachable read, hash check, type check, parse, or path check fails, the algorithm returns before the first delete. This is fail-closed marking. The default SQLite backend performs all deletes in one transaction, so a sweep failure rolls back. The generic `ObjectStore` contract does not require transactional deletion: a loose/custom backend may delete a prefix of unreachable objects and rely on idempotent retry. Reachable objects remain protected by Theorem 2 in both cases.

## 7. Implementation

`chunklog` 0.3.0 is a safe Rust 2021 crate with `#![forbid(unsafe_code)]`. The principal modules are:

- `object`: manual canonical encoding, hashes, typed objects, Tree nodes;
- `store`: verified memory, SQLite, loose-filesystem, and wasm OPFS object stores;
- `repo`: snapshot/change-set commit, traversal, refs, branches, diff, checkout, GC;
- `cli`: staged patch workflow and user commands.

The repository root carries a format-2 `FORMAT` marker. Missing, format-1, and unknown formats are rejected. This deliberately prevents silent interpretation with the wrong physical backend.

The CLI staging directory is a patch: files named `<x>,<z>` are upserts; `.remove` contains one removed coordinate per non-comment line. A coordinate cannot appear in both. Unmentioned chunks survive.

The default `SqliteStore` uses a `WITHOUT ROWID` table keyed by the raw 32-byte address. A repository commit executes `BEGIN IMMEDIATE`, inserts every Blob/Leaf/Branch/Commit with `INSERT OR IGNORE`, commits once under rollback journaling and `synchronous=FULL`, and only then replaces its ref [11,12]. Failure before object commit rolls back; failure between object commit and ref replacement leaves only unreachable objects. The overall operation is not a cross-file transaction. A one-file-per-object store remains available explicitly as `FilesystemStore` for control measurements.

## 8. Evaluation

### 8.1 Research questions

The artifact evaluates:

- **RQ1:** Does the implementation enforce its functional, integrity, path, and GC invariants?
- **RQ2:** How does complete snapshot construction scale independently of filesystem small-file effects?
- **RQ3:** Does k=1 SQLite commit latency remain approximately independent of N over the evaluated range?
- **RQ4:** Is logical checkout independent of N over the evaluated range?
- **RQ5:** What object and byte growth does the persistent tree produce under controlled edits?
- **RQ6:** Can one transaction-batched SQLite CAS remove the file-per-node initial-import bottleneck?
- **RQ7:** Can the opaque-payload interface ingest binary mapblocks emitted by a real voxel engine?

Experiments cannot prove the asymptotic theorems; they test whether the implementation behaves consistently with them over measured ranges.

### 8.2 Environment and method

The reported run used Windows NT 10.0.26200.0, NTFS, an Intel Core i9-13900H with 14 cores/20 logical processors, Rust 1.97.1, Criterion 0.8.2, and the release profile. Criterion used a 1 s warm-up, 3 s target measurement, and 10 samples. Tables report bootstrap median point estimates and Criterion's median confidence interval.

All benchmark worlds contain exactly N coordinates. Payloads are 256 bytes and unique by construction: the coordinate index occupies the first eight bytes and a deterministic generator fills the remainder. Assertions check both cardinality and uniqueness. The naive baseline receives a fresh directory per measured iteration. Checkout alternates between two real branches rather than rewriting the already-current branch.

Derived medians and confidence intervals are in `paper-results/criterion-medians.csv`; experiment notes are in `paper-results/benchmark-summary.md`. Structural growth is regenerated by:

```text
cargo run --release --offline --example paper_artifact
```

### 8.3 Correctness and fault tests

The suite contains 45 integration tests, two CLI unit tests, and one doctest. In addition to ordinary commit/load/branch/diff/GC cases, it checks:

- a deterministic 100-step randomized change sequence against a reference `HashMap`;
- one-coordinate publication of no more than one radix path;
- preservation of unmentioned coordinates and explicit removal;
- Blob tampering detected by load and GC;
- existing corrupt objects rejected on idempotent write;
- path traversal rejected for create/delete/resolve/checkout;
- unsupported repository formats rejected;
- overlapping writers rejected by the repository lock;
- injected marking failure before any delete;
- injected mid-sweep failure followed by successful retry;
- SQLite batch commit and rollback visibility;
- injected object-transaction commit failure before HEAD publication.

All tests, formatting, Clippy with warnings denied, and documentation build are final artifact gates; Section 10 lists the exact commands.

### 8.4 Snapshot algorithm scaling

The verified in-memory backend isolates encoding, hashing, and persistent-tree construction from durable database operations. Repository refs still use a temporary metadata directory.

| N | full-snapshot median | median CI |
| ---: | ---: | ---: |
| 100 | 8.228 ms | 6.944–10.545 ms |
| 1,000 | 22.936 ms | 20.849–24.464 ms |
| 10,000 | 147.431 ms | 137.209–149.577 ms |

The increasing latency is consistent with Proposition 1. These data do not identify a universal throughput because payload size, allocator, hash implementation, coordinate distribution, and backend all matter.

### 8.5 Incremental commit and checkout

| operation | N=100 | N=1,000 |
| --- | ---: | ---: |
| incremental commit, k=1 | 10.446 ms [10.268, 12.132] | 13.577 ms [12.465, 14.660] |
| logical checkout | 5.225 ms [5.147, 5.425] | 7.765 ms [7.351, 8.507] |

Within this limited 10× range, neither k=1 commit nor checkout increases with N. This is consistent with the fixed-depth path bound and logical-reference definition. It is not evidence that all backends, coordinate distributions, histories, or larger scales have identical constants.

Full verified SQLite loads cost 21.221 ms [20.831, 21.956] for N=100 and 222.167 ms [216.701, 231.314] for N=1,000, reflecting traversal, indexed lookup, and verification of every node and Blob.

### 8.6 Initial import scaling across backends

| backend | N=100 | N=1,000 | N=10,000 |
| --- | ---: | ---: | ---: |
| verified memory | 8.228 ms | 22.936 ms | 147.431 ms |
| default SQLite CAS | 14.021 ms | 47.433 ms | 1,156.306 ms |
| loose object files | — | 10,427.392 ms | — |
| raw-file naive baseline | 18.048 ms | 299.824 ms | — |

The loose-file control confirms that the dominant cost is physical publication rather than hashing or tree construction. At N=1,000, SQLite is approximately 220× faster than loose files and 6.3× faster than the feature-incomplete raw-file baseline. The Merkle algorithm and canonical bytes are identical between SQLite and loose stores; the transactional backend replaces thousands of create/write/rename operations with indexed inserts under one durable transaction. The N=10,000 SQLite result remains about 7.8× slower than memory, so database lookup, insertion, and durability overhead remain visible rather than eliminated.

### 8.7 Structural growth

The controlled study begins with N=1,024 chunks and performs R=50 incremental commits with fixed coordinate set and globally unique edited payloads. The edit window rotates. Counts include all history reachable through Commit parents.

| k | Blobs | Branches | Leaves | Commits | total objects | canonical bytes | loose bound |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1,074 | 9,066 | 1,074 | 51 | 11,265 | 804,461 | 19,383 |

| 100 | 6,024 | 48,991 | 6,024 | 51 | 61,090 | 4,166,461 | 108,483 |

## 9. Related Work and Positioning

Git is the immediate conceptual ancestor: typed Blobs, Trees, Commits, immutable object names, and mutable refs. Git's official data-model documentation explicitly describes these object types and snapshot roots [1]. `chunklog` specializes keys to fixed-width coordinates and exposes engine-owned payloads, but this specialization is not a replacement for comparison with Git.

Venti established hash-addressed immutable blocks for archival and deduplication [2]. Foundation demonstrated that the physical CAS layout and disk-operation model materially affect practical performance [3], a lesson reinforced by our file-per-node result. IPFS and other Merkle-DAG systems further generalize content-addressed graphs [4]. Persistent trees and copy-on-write filesystems share unchanged paths or blocks; our fixed-depth radix encoding is one concrete, deliberately simple choice. Content-defined chunking inside payloads (FastCDC [10]) and cross-version deltas are the usual refinements for payload-internal repetition; Section 11 notes that adopting them requires new object types and dependency edges, and therefore new theorems rather than free reuse of ours.

Practical world tooling also predates or overlaps this artifact. GitMC and MineGIT integrate Git-backed world snapshots and branching into Minecraft [5,6]. ChunkSplitter converts a Bedrock database into per-chunk files intended for ordinary version control [7]. Chunker converts between Minecraft world formats [8]. These systems differ in engine coupling, storage unit, materialization, and merge support, but their existence rules out an unqualified “first world version-control system” claim.

`chunklog` is an auditable library experiment in explicit coordinate change sets, persistent coordinate Merkle paths, and failure semantics—not the invention of world versioning or CAS.

## 11. Limitations and Future Work

The current evidence has important limits:

1. **No production-player history.** The Luanti run uses real engine serialization but controlled singlenode generation, not a captured terrain/edit trace. Edit-density and entropy external validity remain open.
2. **One performance host.** Absolute results may differ across filesystems and operating systems.
3. **Residual SQLite overhead.** The dominant loose-file pathology is fixed, but N=10,000 SQLite import remains about 7.8× slower than verified memory and needs profiling before production claims.
4. **Single writer.** The lock does not provide multiplayer or distributed coordination and may remain stale after a process crash.
5. **No cross-file transaction.** SQLite uses rollback journaling and `synchronous=FULL`, but its object transaction and filesystem ref replacement are ordered operations rather than one atomic unit.
6. **No legacy-format migration.** Unversioned and format-1 repositories are rejected.
7. **Diff expands both versions.** A recursive Merkle diff could skip equal subtrees.
8. **No merge, remote protocol, or pruning policy.** Branches provide divergent histories but not reconciliation.
9. **Chunk-level payloads.** Sub-chunk CDC or delta encoding would introduce additional object types and dependency edges; GC and growth theorems would have to be extended rather than assumed unchanged.
10. **Commit metadata bounds.** Logical checkout is O(1) relative to N, not relative to an unbounded Commit message.
11. **OPFS is not evaluated end to end.** A post-evaluation, single-host Chromium microbenchmark covers the wasm append-log `ObjectStore` and normal reopen path. The optimized store retains the complete verified log and temporarily buffers a serialized batch, so browser-memory scaling remains open. Browser-native refs, locks, staging, compaction, cross-browser tests, end-to-end repository measurements, and process-kill recovery remain future work. None of the SQLite performance results is attributed to OPFS.

Immediate future work is prepared-statement and traversal profiling, recursive Merkle diff, real-engine trace evaluation, OPFS compaction and browser integration, explicit recovery tooling, and a migration command. Each changes the relevant cost or failure model and must be evaluated independently.

## 12. Conclusion

Coordinate-addressed versioning can exploit explicit edit locality, but only if its API and data structure preserve that information. In `chunklog` 0.3.0, complete snapshots remain Θ(N), while explicit k-coordinate changes copy a bounded union of sixteen-level radix paths. Typed canonical objects and verified reads strengthen integrity; locking, SQLite object transactions, and ordered ref publication delimit single-writer consistency; GC is sound under stated assumptions and fail-closed during marking.

The evaluation exposes a backend-design lesson: persistent Merkle nodes stored as individual files make initial import much slower than raw copying, whereas one SQLite transaction reduces N=1,000 import from 10.427 s to 47.433 ms. The appropriate conclusion is not that content addressing makes every operation faster, but that explicit change sets and structural sharing reduce incremental work only when the physical object layout avoids pathological small-file amplification.

## Appendix A. Post-evaluation OPFS microbenchmark

After the main 0.3.0 evaluation, we added a wasm-only append-log `ObjectStore`
and a reproducible Dedicated Worker benchmark. On one Windows 11 host with
headless Chromium 131, unique 256-byte objects produced the following medians:

| Mode | N | Import | Reopen and rebuild index | Verified cached full read |
| --- | ---: | ---: | ---: | ---: |
| one explicit batch | 100 | 0.9 ms | 2.0 ms | 0.1 ms |
| one transaction per object | 100 | 46.3 ms | 1.5 ms | 0.1 ms |
| one explicit batch | 1,000 | 3.3 ms | 2.7 ms | 0.7 ms |
| one transaction per object | 1,000 | 415.4 ms | 3.0 ms | 0.6 ms |
| one explicit batch | 10,000 | 39.0 ms | 18.6 ms | 13.5 ms |

The initial OPFS implementation issued one synchronous write per object even
inside an explicit batch and repeated that boundary crossing on reads. Staging
the final transaction in wasm and emitting one write/flush reduced batched
import from 446.9 ms to 3.3 ms at N=1,000 and from 5,069.7 ms to 39.0 ms at
N=10,000. Retaining the already verified log as the coherent read cache reduced
the N=10,000 full-read median from 2,964.0 ms to 13.5 ms. The tradeoff is linear
resident log memory plus temporary pending and serialized batch buffers.

This workload writes raw object-store payloads, whereas the native SQLite table
measures a complete Repository snapshot with Merkle construction, so the two
tables are not directly comparable. The browser study is single-host and
fixed-order, and normal close/reopen is not a power-loss test. Three-stage raw
samples, quartiles and reproduction instructions are archived in
`paper-results/opfs-benchmark-summary.md`.
